本次连续授权的实施范围包括此前 P0 来源归属修复、F04 派生 Schema 一致性、独立 API 配置保存，以及后来明确要求的澄湾前端设计移植。其他 P1 / P2 方案没有一并实施；未修改澄湾维护源，也未发布运行资源。

## 已完成的行为

- P0：保留来源检查，区分存档 `message`、活动 `swipe`、逻辑玩家输入和出站提示词。有原文归属凭据的 advice 搬运可继续原请求；真实编辑、删除、换候选或换聊天仍使旧结果失效。只在本次正文创建完成时封存首次保存读回，不能在后续重试中重新绑定已编辑的上下文。待结算正文携带原提交身份，沿用既有 pending / prepared / journal 和保存确认机制。任意预设的未知持久化改写仍需实际证据，未按预设名字放行。
- F04：通过现有 `工具/生成派生产物.mjs` 重建 `schema.json`，由旧 142 个 defs 更新为当前生成器的 22 个。运行 `schema.ts`、initvar 及旧别名迁移未改；旧输入别名仍可由运行 Schema 接收，但不进入当前模型输入定义。
- API：酒馆账号服务器文件加当前浏览器副本，使用独立的 `valoran-v1-api-variable/phone/information.json` 文件名，以及带账号作用域的浏览器键。服务器写入后完整读回，再写浏览器副本并读回；服务器失败不覆盖旧副本。服务器已确认而浏览器副本失败时，采用已确认值并明确提示部分保存结果。旧角色变量“澄湾设置”仍可读取，不机械改兼容键。
- 请求职责：正文继续使用酒馆主模型；正文变量、手机与奇遇继续使用本卡既有流程。资料选择默认复用变量连接，也支持独立端点。保存、读取配置不会生成正文或结算变量。每次只采纳当前通道的确认值，避免两个表单先后完成时互相回滚。
- 前端：直接移植澄湾当前公共设计系统及 23 份前端文件的展示或样式代码；此前另已移植 API 折叠区及表单。设置使用四栏等宽导航，资料调度分为角色、地点和组织子页，旧入口仍定位到对应区。同步建档底栏、档案与物品卡、任务及商店、手机外框等响应式设计；玩家记录详情挂载到可见界面根内。

瓦罗兰的种族、身份、金币与蓝色精粹、角色配额及轮换语义、地图画布和坐标、已有四个 App、已有存档和业务事件保持本卡契约。未随设计移植上海字段、人物联合选择、生活补更、新 App、删除任务、停止刷新或建档预设共享功能。
